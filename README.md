# RISE API MVP

The PostgreSQL/Docker MVP is implemented alongside the compatible `/v1` demo. Start with [the runbook](docs/runbook.md), [API guide](docs/api.md), and [architecture](docs/architecture.md).

```sh
python scripts/migrate_env.py
docker compose up --build -d
docker compose --profile setup run --rm models
```

Set `RISE_ADMIN_TOKEN` in `.env` for admin APIs. Swagger is at `http://127.0.0.1:8077/docs`; the generated read-only `/v2` contract is at `/design/docs`. Docker runtime data comes from PostgreSQL 17/pgvector, with private PDF and model volumes. `/v1` keeps templates/personas/SSE; `/v2` adds versioned review, facts/rules, leased jobs, hybrid retrieval and verified model/fallback answers.

The material below documents the original standalone JSON demo and historical measurements. For current deployment and limitations use the linked MVP runbook. Unreviewed source facts remain unreviewed; passing tests is not evidence of research answer quality.

# COCO-RISE demo

เอกสารออกแบบ MVP และ Swagger ของระบบเป้าหมายอยู่ที่ [docs/README.md](docs/README.md) — แยกจาก API ของเดโมที่ทำงานอยู่

**อัปเดตล่าสุด:** 2026-10-18

COCO-RISE คือชื่อระบบที่ใช้ต่อจากชื่อเดิม RISE ชื่อโฟลเดอร์และตัวแปรตั้งค่า `RISE_*` ยังใช้แบบเดิมในระยะเปลี่ยนชื่อ เพื่อไม่ให้การติดตั้งเดิมหยุดทำงาน

ระบบตอบคำถามทุนวิจัยของวิทยาลัยการคอมพิวเตอร์ ทำตามภาพสถาปัตยกรรมฉบับย่อ คือ วิเคราะห์คำถาม ค้นคืนหลักฐาน สร้างคำตอบ แล้วตรวจก่อนส่ง
ระบบทำงานใน **fail-closed safe mode** คำตอบทั้งหมดมาจาก template ที่โค้ดประกอบจากข้อความ ข้อเท็จจริง และกฎที่คนตรวจแล้ว จากนั้น `pipeline.verify` ตรวจซ้ำก่อนส่ง ระบบไม่ใช้ LLM เขียนหรือเรียบเรียงคำตอบอิสระ

Ollama กับ `bge-m3` เป็นตัวเลือกสำหรับค้นเชิงความหมายเท่านั้น หากไม่มี ระบบยังตอบได้ด้วยการค้นคำสำคัญ trigram และข้อมูลเชิงโครงสร้าง โดยไม่ลดกติกาการตรวจคำตอบ

หากต้องการลองใช้งานทันที อ่าน[คู่มือเดโมฉบับสั้น](DEMO_GUIDE.md)ก่อน โดยเฉพาะข้อจำกัดของประกาศสแกนที่ยังรอคนตรวจ

ถ้าต้องการใช้เวกเตอร์และยังไม่มีโมเดล

```bash

```

## วิธีรัน

```powershell
pip install -r requirements.txt
.\run.ps1
```

`run.ps1` สร้าง `.env` จาก `.env.example` เมื่อยังไม่มี แล้วโหลดค่าจาก `.env` ให้อัตโนมัติก่อนตรวจความพร้อมและเปิดเซิร์ฟเวอร์ ไม่ต้องโหลดตัวแปรเข้า PowerShell เอง ค่าที่สคริปต์โหลดหรือปรับสำหรับโหมดเพื่อนจะถูกคืนเมื่อสคริปต์จบ จึงแก้ `.env` แล้วรันใหม่ในหน้าต่างเดิมได้โดยไม่ติดค่ารอบก่อน การถามตอบพื้นฐานไม่ต้องมี Ollama หรือสร้างเวกเตอร์ก่อน หากต้องการใช้การค้นเชิงความหมายและติดตั้ง Ollama กับ `bge-m3` แล้ว จึงค่อยรัน `.\run.ps1 -Reindex`

สคริปต์รายงานสถานะ Ollama และ `bge-m3` เป็นข้อมูลประกอบ เพราะสองอย่างนี้เป็นส่วนเสริม ไม่ใช่เงื่อนไขของการตอบแบบปลอดภัย ถ้าอยากตรวจความพร้อมเฉย ๆ ใช้ `.\run.ps1 -Check` หรือ `python check.py`

### ให้เพื่อน clone ไปรันบนเครื่อง Windows

repo นี้เป็น Private จึงต้องเชิญบัญชี GitHub ของเพื่อนเป็น collaborator ก่อน เมื่อเพื่อนรับคำเชิญแล้วให้รัน

```powershell
git clone https://github.com/BossZY27/COCO-RISE.git
cd COCO-RISE
python -m pip install -r requirements.txt
.\run.ps1
```

เปิด `http://127.0.0.1:8077/` บนเครื่องของเพื่อน ข้อมูลตัวอย่างที่ใช้ตอบอยู่ใน `data/` ของ repo แล้ว หาก PowerShell ไม่อนุญาตให้รัน `run.ps1` สามารถใช้ `python -m uvicorn app.main:app --host 127.0.0.1 --port 8077` แทนได้ โดยไม่ต้องใช้ Ollama เช่นกัน อย่าใช้ตัวเลือก `-FriendDemoIp` สำหรับกรณีนี้ เพราะตัวเลือกนั้นใช้เปิดจากเครื่องหนึ่งให้คนอื่นใน LAN เข้า ไม่ใช่การรันแยกบนเครื่องของเพื่อน

### ให้เพื่อนใน Wi-Fi เดียวกันลอง

หา private IPv4 ของเครื่องจาก `Get-NetIPAddress -AddressFamily IPv4` แล้วระบุ IP นั้นโดยตรง เช่น

```powershell
.\run.ps1 -FriendDemoIp 192.168.1.25
```

โหมดนี้รับเฉพาะ IP ช่วง private LAN ที่มีอยู่บน network adapter ของเครื่อง ไม่ผูกกับ `0.0.0.0` และรัน worker เดียว โหมดนี้บังคับใช้ persona สมมติ ไม่เชื่อ `X-User-Id` จากเครื่องลูกข่าย ปิด `/admin` ปิด API docs และปิด audit log หากต้องเก็บคำถามสำหรับการทดสอบ ให้เพิ่ม `-FriendDemoAudit` หลังแจ้งผู้ทดลองก่อน เมื่อ audit ปิด ปุ่มความเห็นจะแจ้งตรง ๆ ว่าเดโมไม่ได้เก็บข้อมูล

สคริปต์ไม่เปิด Windows Firewall และไม่สร้าง tunnel หากเพื่อนเข้าไม่ได้ เจ้าของเครื่องต้องเปิดพอร์ตเฉพาะเครือข่าย Private ด้วยตนเองและปิดกฎหลังจบเดโม วิธีนี้ใช้กับ LAN ที่ไว้ใจได้เท่านั้น อย่า forward พอร์ต 8077 ออกอินเทอร์เน็ต

บนระบบอื่นหรืออยากสั่งเอง

```bash
pip install -r requirements.txt
python reindex.py
python -m uvicorn app.main:app --port 8077
```

`reindex.py` ฝังเวกเตอร์ทุกชิ้นครั้งเดียวแล้วเก็บลง `data/embeddings.json` รันซ้ำจะฝังเฉพาะชิ้นที่ข้อความเปลี่ยน คำสั่งนี้ต้องใช้ Ollama กับ `bge-m3`; การตอบแบบ trigram ไม่ต้องใช้ไฟล์เวกเตอร์ ไฟล์ embeddings เป็น derived cache หากเสียหรือรูปแบบผิด ระบบจะสร้างใหม่ การเขียนแต่ละ batch ใช้ไฟล์ชั่วคราวแล้วแทนที่แบบ atomic ตรวจจำนวน ค่า และมิติของเวกเตอร์ก่อนรับ และลบรายการของ chunk ที่ไม่มีอยู่แล้วออกจาก cache
เมื่อเปิดเซิร์ฟเวอร์ การเตรียม vector cache ทำใน background และไม่บล็อก startup ระหว่างนั้นคำถามใช้ keyword, trigram และ structured lookup ได้ตามปกติ

เปิด http://127.0.0.1:8077 แล้วเลือกผู้ใช้สมมติ จากนั้นพิมพ์คำถาม เช่น

- มีทุนอะไรบ้าง
- เพดานของทุนวิจัยสถาบันตามหลักเกณฑ์กลางคือเท่าไร
- เงินสมทบหมายถึงอะไร
- ทุนวิจัยสถาบันคืออะไร

ลองถาม "ทุนวิจัยสถาบันปี 2569 ให้ทุนละเท่าไร" เพื่อตรวจพฤติกรรมเมื่อวงเงินรายปียังรอคนอนุมัติ ระบบแสดงได้เฉพาะเพดานตามหลักเกณฑ์กลางที่ตรวจแล้ว พร้อมบอกว่าไม่ใช่วงเงินจัดสรรรายปี ส่วน "ขอทุนวิจัยในชั้นเรียนได้ไหม" ต้องตอบว่ายังสรุปสิทธิ์ไม่ได้ เพราะกฎจากประกาศสแกนยังรอตรวจ
คำถาม "สมัครยังไง/ต้องใช้เอกสารอะไร" จะบอกตรง ๆ ว่าเดโมยังไม่มีข้อมูลที่ตรวจแล้ว และคำถามเรื่องสิทธิ์ของทุนที่ไม่มีกฎที่ตรวจแล้วจะไม่ถูกพาไปตอบเรื่องวงเงิน

ทดสอบตรรกะและคำตอบ deterministic ด้วยคำสั่งต่อไปนี้

```bash
python -m pytest tests -q
python eval.py
python eval_quality.py
```

`tests/` ตรึงพฤติกรรมที่ตัดสินว่าคำตอบจะเป็นอย่างไร คือการจับชื่อทุน การแยกเจตนา การเลือกแถวข้อมูล
การตรวจสิทธิ์ รวมกติกาข้ามทุน และขั้นตรวจคำตอบ ชุดนี้ไม่เขียนทับไฟล์ใน `data/` เลย

หน้าเว็บไม่มีตัวเลือกโมเดลตอบ และเซิร์ฟเวอร์ไม่อุ่นโมเดลเขียนคำตอบ `benchmark_models.py` และ `eval_quality.py --llm` จบแบบ fail-fast ด้วย exit code 2 ใน safe mode การเปรียบเทียบโมเดลจะเปิดอีกครั้งเมื่อมี typed-claim renderer ที่บังคับ schema และตรวจทุก claim ก่อน render เท่านั้น ห้ามนำผลเก่ามาอ้างเป็นผลของรุ่นนี้

## สี่ขั้นตอนตามภาพสถาปัตยกรรม

| ขั้นตอน | ไฟล์ | ทำอะไร |
|---|---|---|
| 1 วิเคราะห์คำถาม | `app/modules/query/engine.py`, `patterns.py` | เขียนคำถามต่อเนื่องให้สมบูรณ์ หาชื่อทุน ชั้น ปีงบ และเจตนาด้วยกติกา deterministic |
| 2 ค้นคืนหลักฐาน | `app/modules/retrieval/`, `app/modules/knowledge/corpus.py` | ยิงขนานสามทาง คือคำสำคัญ BM25 ความหมายด้วย bge-m3 และข้อเท็จจริงเชิงโครงสร้าง แล้วรวมด้วย RRF |
| 3 สร้างคำตอบ | `app/modules/query/composer.py`, `answers.py` | ตรวจสิทธิ์จากกฎกับโปรไฟล์ แล้ว render template จากแถวที่ตรวจแล้ว |
| 4 ตรวจแล้วส่งกลับ | `app/modules/query/verification.py` | ตรวจตัวเลข ปีงบ ชื่อทุน เงื่อนไข และอ้างอิง หากไม่ผ่านจะตอบแบบ blocked โดยไม่ส่งข้อความที่ตรวจไม่ผ่าน |

เวลาแก้โค้ด ให้เลือกส่วนตามหน้าที่: `app/main.py` ประกอบ API, `app/modules/legacy/` รักษา `/v1`, `app/static/` เก็บหน้าจอ, `app/modules/query/` วิเคราะห์และตรวจคำตอบ, `app/modules/documents/` ตรวจ PDF/review/publish, `app/workers/` ทำ ingestion/indexing และ `app/infrastructure/` เชื่อม PostgreSQL, Ollama, filesystem และ JSON fixtures รายละเอียดแผนผังอยู่ใน `docs/project-structure.md`

จุดที่ต่างจาก RAG ทั่วไปและเป็นหัวใจของโปรเจกต์

- **ไม่มี free-form answer LLM ในเส้นทางตอบ** โค้ดเลือกข้อมูลที่ตรวจแล้วและ render ถ้อยคำที่กำหนดไว้ จึงไม่มีร่างจากโมเดลให้หลุดถึงผู้ใช้
- **แยก `amount_type`** เป็น `ceiling` เพดานตามหลักเกณฑ์กลาง กับ `allocated` วงเงินจริงของปีงบนั้น ถ้าวงเงินรายปียังรอตรวจ จะไม่ตอบตัวเลขรายปี แต่บอกเพดานที่ตรวจแล้วพร้อมแยกความหมายชัดเจน
- **กรองเอกสารด้วยปีงบและการอนุมัติก่อนค้น** ชิ้นที่ยัง `draft` หรือไม่ได้ระบุ `verified: true` เป็น JSON boolean อย่างชัดเจนจะไม่ถูกค้นเจอ ค่า `verified` ที่หายหรือผิดรูปแบบถือว่ายังรอตรวจ และกฎจากประกาศสแกนยังไม่ใช้จนกว่าคนอนุมัติข้อความของฉบับนั้น
- **ตรวจสิทธิ์ด้วยกฎที่เก็บเป็นข้อมูล** `data/rules.json` ไม่ใช้โมเดลเดา ผลจึงเหมือนเดิมทุกครั้งและทดสอบได้
- **ไม่ตอบตัวเลขที่ยังไม่ได้ตรวจ** แถวที่ `verified` เป็น false จะไม่เข้าสู่ตัว render หรือแสดงวงเงินรายปี ระบบแจ้งว่าประกาศสแกนยังรอเจ้าหน้าที่อนุมัติ และอาจแสดงเพดานจากแถวอื่นที่ตรวจแล้ว

## เวลาที่ต้องวัดใหม่

ต้องวัดเวลาใหม่หลัง safe mode ชุดสุดท้าย โดยแยกกรณีใช้ `bge-m3` กับกรณีถอยไปใช้ trigram ตัวเลขจากเส้นทาง LLM รุ่นก่อนใช้กับสถาปัตยกรรมนี้ไม่ได้

| ขั้นตอน | เวลา | หมายเหตุ |
|---|---|---|
| วิเคราะห์คำถาม | ต้องวัดใหม่ | ใช้กติกา deterministic |
| ค้นคืนหลักฐาน | ต้องวัดใหม่ | `bge-m3` เป็นตัวเลือก; trigram เป็นทางถอย |
| ตรวจสิทธิ์และ render คำตอบ | ต้องวัดใหม่ | อ่านกฎและข้อมูลที่ตรวจแล้ว |
| ตรวจคำตอบ | ต้องวัดใหม่ | ตรวจหลักฐานก่อนส่ง |

SSE ส่งคำตอบเดียวกับ endpoint ปกติจาก template ที่ผ่านด่านตรวจแล้ว ไม่มี token หรือร่างจากโมเดลระหว่างทาง

### บันทึกข้อผิดพลาดที่เกิดขึ้นระหว่างพัฒนา

รอบแรกที่รัน `scripts/ingest.py` มันทิ้งข้อย่อยในตารางหน้า 4 ไปเงียบ ๆ เพราะเงื่อนไขเดิมเก็บเฉพาะข้อความยาวเกิน 40 ตัวอักษร
แถวอย่าง `1.6.1 ระดับต้น ไม่เกิน 150,000 บาท` ยาว 33 ตัวอักษร จึงหลุดออกไป
ผลคือหน้า 4 เหลือแต่ข้อ 1.6 ที่เขียนแค่วงเงินรวม 1,000,000 บาท แล้วสรุปผิดว่าเอกสารไม่ได้แยกเพดานตามชั้น

เอกสารจริงมีข้อ 1.6.1 ถึง 1.6.3 และ 1.11.1 ถึง 1.11.3 ครบ ตัวเลข 150,000 / 200,000 / 250,000 ถูกต้องมาตลอด
แก้แล้วโดยแยกเกณฑ์ความยาวเป็นสองค่า ข้อที่มีเลขกำกับเก็บตั้งแต่ 12 ตัวอักษร ส่วนข้อความที่ไม่มีเลขกำกับยังใช้ 40 เท่าเดิม

บทเรียนที่ใช้ได้กับระบบจริง การสกัดข้อมูลที่ทิ้งของเงียบ ๆ อันตรายกว่าการสกัดที่พัง
ถ้ามันพังจะเห็นทันที แต่ถ้ามันทิ้งไปเฉย ๆ จะดูเหมือนเอกสารไม่มีข้อนั้น ตอนทำ OCR ประกาศที่เหลือต้องระวังจุดนี้ซ้ำ

## คำถามแบบไหนที่ระบบตอบได้ และแบบไหนที่ยังไม่ได้

ตอนนี้ระบบรู้จักคำถามสี่แบบ แบ่งจากคำที่อยู่ในคำถาม

| เจตนา | ตัวอย่างคำถาม | ตอบจากอะไร |
|---|---|---|
| `amount` | ทุนนี้ปีนี้ได้เท่าไร | แถว allocated ของปีที่ถาม |
| `ceiling` | เพดานตามหลักเกณฑ์กลางคือเท่าไร | แถว ceiling |
| `eligibility` | พระขอได้มั้ย, ใครขอได้บ้าง, ขอเพิ่มอีกทุนได้ไหม | กฎใน rules.json ถ้าระบุทุน หรือนิยามผู้ขอรับทุนถ้าไม่ระบุ |
| `definition` | เงินสมทบหมายถึงอะไร, ทุนวิจัยสถาบันคืออะไร | ข้อนิยามหรือหมวดทุนจากบัญชีแนบท้ายที่ตรวจแล้ว |
| `list` | มีทุนอะไรบ้าง, ทุนมีกี่ประเภท | รายชื่อทุนทั้งหมดจากบัญชีแนบท้าย แยกสองหมวด |
| `application` | สมัครยังไง, ต้องใช้เอกสารอะไร | แจ้งว่าเดโมยังไม่มีขั้นตอนหรือเอกสารที่ตรวจแล้ว ไม่ตอบเรื่องเงินแทน |

คำว่า “ปีนี้”, “ปีหน้า” และ “ปีก่อน” คำนวณปีงบไทยตามเขตเวลา Asia/Bangkok ใหม่ทุก request และเปลี่ยนปีในวันที่ 1 ตุลาคม เซิร์ฟเวอร์ที่เปิดข้ามวันจึงไม่ค้างปีเก่า ส่วนคำถามที่ไม่ระบุปีใช้ `RISE_FISCAL_YEAR` ซึ่งหมายถึงปีของชุดข้อมูลรายปีล่าสุดที่ตรวจแล้ว ไม่ใช่เวลาปัจจุบันโดยอัตโนมัติ

ระยะเดโมนี้ยังไม่แนะนำหรือเลือกทุนให้จากลักษณะงานหรือข้อมูลส่วนบุคคล คำถามที่ขอให้แนะนำ
หรือบอกความต้องการโดยไม่ระบุทุน จะได้รับคำชี้แจงให้เปิดรายการทุนทั้งหมดและถามต่อด้วยชื่อทุน
ระบบยังค้นรายการตามหัวข้อที่ระบุชัดในข้อความเอกสารที่ตรวจแล้วได้ เช่น “ทุนเกี่ยวกับการสอนมีอะไรบ้าง”
แต่การปรากฏในรายการตามหัวข้อไม่ใช่คำแนะนำเฉพาะบุคคลหรือการยืนยันสิทธิ์

คำถามอย่าง "พระขอได้มั้ย" ระบบตอบด้วยนิยามผู้ขอรับทุนพร้อมอ้างอิง ไม่ได้ตอบว่า "พระขอไม่ได้"
เพราะเอกสารเขียนไว้ว่าใครขอได้ ไม่ได้เขียนว่าใครขอไม่ได้ และพระที่เป็นบุคลากรของวิทยาลัยก็ยังเข้านิยาม
ระบบจึงบอกเกณฑ์แล้วให้ผู้อ่านเทียบเอง การเติมคำตอบที่เอกสารไม่ได้เขียนคือสิ่งที่ระบบนี้ถูกออกแบบมาเพื่อไม่ให้เกิด

คำถามเรื่องการสมัคร เช่น "ต้องใช้เอกสารอะไรบ้าง" หรือ "ปิดรับสมัครเมื่อไร" ถ้าระบุชื่อทุน ระบบจะบอกว่าข้อมูลนี้ยังไม่อยู่ในฐานข้อมูลเดโมที่ตรวจแล้ว
ถ้าไม่ระบุชื่อทุน ระบบจะขอให้ระบุทุนก่อน ขั้นตอนถัดไปคือเก็บข้อมูลวันเปิดปิดรับและเอกสารที่ต้องใช้จากประกาศที่ตรวจแล้ว

การจับชื่อทุนใช้เกณฑ์ความคล้าย 0.80 ขึ้นไป วัดจากคำถามจริงแล้วคำถามที่ระบุชื่อทุนถูกต้องได้ 0.833 ขึ้นไปทุกข้อ ส่วนคำถามที่ไม่ได้ระบุชื่อทุนสูงสุดอยู่ที่ 0.750
คำถามที่พูดว่า "ทุนนี้" หรือ "ทุนดังกล่าว" ระบบจะไม่เดาชื่อทุนจากตัวคำถาม แต่ย้อนไปหาจากบทสนทนาก่อนหน้าแทน

## กติกาสิทธิ์ รวมกติกาข้ามทุน

`data/rules.json` เก็บกติกาเป็นข้อมูล ไม่ใช่โค้ด เพิ่มกติกาใหม่ได้โดยไม่ต้องแก้โปรแกรม
แต่ละกติกาผูกกับทุนหนึ่งทุน มีรายการเงื่อนไข และมีแหล่งอ้างอิงที่ชี้ไปหน้าและข้อในเอกสาร

| op | หมายความว่า | ตัวอย่าง |
|---|---|---|
| `in` | ค่าต้องอยู่ในรายการ | ประเภทบุคลากรต้องเป็นข้าราชการ พนักงาน หรือลูกจ้าง |
| `eq` | ค่าต้องตรงกัน | ต้องสังกัดวิทยาลัยการคอมพิวเตอร์ |
| `lt` | จำนวนต้องน้อยกว่า | ปีนี้ต้องยังได้ทุนนี้ไม่ถึง 1 ทุน |
| `not_received` | **ห้ามเคยได้ทุนในรายการนี้** | ได้เงินรางวัลหมวด 2.2 แล้ว ขอหมวด 2.3 ไม่ได้ |

`not_received` คือกติกาข้ามทุน เขียนรายชื่อทุนที่เป็นตัวบล็อกไว้ในช่อง `value` ได้หลายทุน
ถ้าผู้ถามเคยได้ทุนใดทุนหนึ่งในรายการ ระบบจะตอบว่าไม่เข้าเกณฑ์และบอกด้วยว่าติดเพราะทุนไหน โดยใส่ `{fund}` ลงใน `fail_reason`

ตอนนี้มีกติกาข้ามทุนหนึ่งข้อที่ยืนยันจากเอกสารจริงได้ คือหลักเกณฑ์กลางบัญชีแนบท้ายข้อ 2.2 หน้า 5 เขียนว่า
"กรณีได้รับเงินรางวัลใน 2.2 แล้วจะไม่สามารถขอเงินรางวัลในหมวด 2.3 ได้"
กติกาข้ามทุนข้ออื่นน่าจะอยู่ในประกาศประจำปีซึ่งยังเป็นภาพสแกน ต้อง OCR แล้วอ่านก่อนจึงจะเพิ่มได้ อย่าเดา

## เพิ่มเอกสารจริงเข้าระบบ

หน้า `/admin` มีช่อง **ตรวจ PDF ใหม่ก่อนนำเข้าระบบ** สำหรับอัปโหลดเพื่อดูข้อความรายหน้าและตัวเลขที่อาจเป็นวงเงิน ผลนี้เป็นเพียงตัวอย่างให้คนเทียบกับต้นฉบับ ไม่บันทึกไฟล์ ไม่เพิ่มข้อมูลให้บอทตอบ และไม่อนุมัติอัตโนมัติ รองรับ PDF สูงสุด 15 MB และ 50 หน้า ถ้าหน้าเป็นภาพสแกนจะลอง OCR; หาก OCR ใช้งานไม่ได้ ระบบจะแจ้งว่าหน้านั้นยังอ่านไม่ได้

ช่อง **นำเข้า PDF เป็นฉบับร่าง** จะเก็บไฟล์ไว้ในพื้นที่กักกันแบบถาวร แล้วส่งเข้าคิวเบื้องหลังที่อ่านทีละไฟล์ ข้อความถูกเรียงตามหน้าและข้อ แบ่งชิ้นไม่เกิน 900 ตัวอักษร จัดประเภทเป็นหัวเรื่อง นิยาม รายการทุน วงเงิน คุณสมบัติ วิธีสมัคร กำหนดการ ช่องทางติดต่อ หรืออื่น ๆ เมื่ออ่านครบทุกหน้าและสถานะเป็น `awaiting_review` เจ้าหน้าที่จึงแก้ข้อความกับประเภทได้ ทุกชิ้นเริ่มเป็น `draft`, `verified: false` และ `published: false` เสมอ การแก้ข้อความไม่ใช่การอนุมัติ

พื้นที่กักกันรับค่าเริ่มต้นไม่เกิน 100 เอกสารและ PDF ต้นฉบับรวม 512 MiB ตรวจโควตาภายใต้ lock ก่อนบันทึก เนื้อหาที่มี SHA-256 ซ้ำยังคืนรายการเดิมได้แม้โควตาเต็ม โควตานับเฉพาะไฟล์ PDF ใน `documents/` ไม่รวม metadata, chunks หรือไฟล์ชั่วคราว

สถานะงานมี `queued`, `extracting`, `chunking`, `awaiting_review`, `needs_ocr` และ `failed` ไฟล์เดิมที่อัปโหลดซ้ำจะอ้างงานเดิมด้วยค่า SHA-256 จึงไม่สร้างสำเนาซ้ำ หากบางหน้าอ่านไม่ได้ ระบบยังเก็บส่วนที่อ่านได้ให้เปิดดู แต่ล็อกการแก้จนกว่าจะลอง OCR ใหม่สำเร็จ เพื่อไม่ให้การประมวลผลซ้ำเขียนทับงานคน เอกสารและชิ้นข้อความฉบับร่างอยู่ใต้ `RISE_INGESTION_DIR` ซึ่งค่าเริ่มต้นคือ `data/ingestion/` และไม่ถูกโหลดเข้า `store.CHUNKS`, `facts.json`, `rules.json` หรือเวกเตอร์ค้นหา

เมื่อเปิดเซิร์ฟเวอร์ใหม่ ระบบจะอ่านสถานะที่บันทึกไว้ สร้างระเบียนงานที่อาจขาดหายจากการหยุดกลางคัน และทำงาน `queued`/`extracting`/`chunking` ต่อ งาน `needs_ocr` หรือ `failed` ต้องให้เจ้าหน้าที่กด **ลองประมวลผลอีกครั้ง** งาน OCR และตรวจ PDF ถูกจำกัดด้วยคิว FIFO ให้ทำทีละงานต่อหนึ่งโปรเซสเพื่อไม่แย่ง CPU กับการถามตอบ

เมื่ออ่านครบทุกหน้าแล้ว ผู้ดูแลเปิด PDF ต้นฉบับเทียบข้อความทุกหน้า ทำเครื่องหมายยืนยันแต่ละหน้า และกด **อนุมัติข้อความและเผยแพร่** พร้อมชื่อผู้ตรวจ ระบบเทียบ SHA-256 ของไฟล์จริงกับรายการที่ตรวจ แล้วค่อยเพิ่มข้อความลง `data/chunks_published.json` และดัชนีค้นของโปรเซสนี้ ขั้นอัปโหลดหรือการแก้ฉบับร่างเพียงอย่างเดียวไม่เผยแพร่ข้อมูล หาก OCR อ่านหน้าใดไม่ครบจะกดอนุมัติไม่ได้

การเผยแพร่นี้ครอบคลุม **ข้อความหลักฐานเท่านั้น** ไม่สกัดตัวเลขเป็น `facts.json` ไม่สร้างกฎใน `rules.json` และไม่รับรองว่า PDF ใหม่ทุกฉบับจะตอบคำถามได้ครบ ชื่อทุนใหม่ วงเงินจัดสรรรายปี เงื่อนไขสิทธิ์ และคำตอบตามหัวข้อที่ยังไม่มี template ต้องเพิ่มข้อมูลโครงสร้างและทดสอบแยกกันโดยคนตรวจ เพดานกลางกับวงเงินจัดสรรรายปียังคงแยกกันเสมอ การสร้างเวกเตอร์ด้วย `python reindex.py` เป็นขั้นเสริมภายหลัง; ข้อความที่อนุมัติแล้วค้นผ่านคำสำคัญและลำดับชั้นได้ทันที

สำหรับเอกสารเดิมที่นำเข้าผ่านสคริปต์และยังรอตรวจ ให้ใช้ขั้นตอนเดิมโดยผู้รับผิดชอบ:

```bash
python scripts/ingest.py --src "<โฟลเดอร์ที่เก็บ PDF>" --out data/chunks_ingested.json
python scripts/verify_report.py
python reindex.py
```

ข้อความทุกชิ้นที่นำเข้าใหม่เริ่มเป็น `draft` และ `verified: false` แม้อ่านจากชั้นข้อความของ PDF ได้ เพราะการอ่านออกไม่ได้ยืนยันว่าเอกสารหรือข้อความถูกต้อง ชิ้นในพื้นที่กักกันจะไม่ถูกค้นเจอจนกว่าคนจะกดเผยแพร่หลังตรวจทุกหน้า

OCR จะใช้ Tesseract ภาษาไทยถ้ามี หรือใช้ easyocr เป็นทางสำรอง บนเครื่องปัจจุบัน Tesseract ยังไม่มี แต่ easyocr ใช้ได้ (ทดสอบ 29 ก.ย. 2569) หน้าที่เป็นภาพสแกนจึงอ่านได้ แต่ใช้เวลาหลายสิบวินาทีต่อหน้าบน CPU ถ้า OCR ล้มเหลว หน้าเว็บจะระบุว่า `OCR อ่านไม่ได้` โดยไม่เดาข้อความหรืออนุมัติข้อมูล

ตัวเลขวงเงินไม่มีสคริปต์ไหนเขียนลง `data/facts.json` ให้ `scripts/verify_report.py` ทำได้แค่หาบรรทัดที่มีตัวเลขนั้นมาวางให้ดู
คนต้องอ่านแล้วกดยืนยันเองที่ `/admin` เพราะ OCR อ่านเลขผิดได้ และนี่คือขั้นตอน human review ในภาพสถาปัตยกรรม

## ระบบรู้จักผู้ถามได้อย่างไร

เดโมตรวจเงื่อนไขสิทธิ์จากข้อมูลผู้ใช้สมมติหกคนใน `data/personas.json` เพื่อแสดงการทำงานของกฎเท่านั้น ส่วนนี้ไม่ใช่ระบบจับคู่ทุนตามโปรไฟล์ ไม่รับประกันสิทธิ์หรือผลอนุมัติ และยังไม่ได้เชื่อมฐานข้อมูลบุคลากรของมหาวิทยาลัย

| id | ใคร | ใช้ทดสอบอะไร |
|---|---|---|
| P1 | พนักงานมหาวิทยาลัย สังกัดวิทยาลัยการคอมพิวเตอร์ ยังไม่รับทุนปีนี้ | เส้นทางปกติ มีสิทธิ์ |
| P2 | เหมือน P1 แต่รับทุนความเป็นเลิศไปแล้ว 1 ทุน | กติกาขอได้คนละ 1 ทุนต่อปี |
| P3 | ลูกจ้างมหาวิทยาลัย | นิยามผู้ขอรับทุนครอบคลุมลูกจ้าง |
| P4 | สังกัดคณะอื่น | ไม่เข้าเกณฑ์สังกัด |
| P5 | ยังไม่กรอกข้อมูล | ต้องตอบแบบมีเงื่อนไข ไม่ใช่ปฏิเสธ |
| P6 | พนักงานมหาวิทยาลัยที่รับเงินรางวัลการตีพิมพ์ในฐานะผู้แต่งชื่อแรกแล้ว | ทดสอบกฎ `not_received` ที่กันการขอเงินรางวัลผู้ประพันธ์บรรณกิจหลังได้รับรางวัลผู้แต่งชื่อแรก |

หากพัฒนาต่อและได้รับอนุญาตให้เชื่อมระบบจริง จุดเชื่อมข้อมูลผู้ใช้คือ `identity.lookup` แต่ต้องกำหนดนโยบายข้อมูลส่วนบุคคล การยืนยันตัวตน และการรับรองผลกฎก่อนใช้งานจริง
ผู้เรียกต้องส่ง `X-User-Id` มาทาง header ซึ่ง reverse proxy เป็นคนใส่หลังตรวจ session แล้ว
ค่าที่ส่งมาใน body จะถูกใช้ก็ต่อเมื่อไม่มี header เพื่อให้หน้าเว็บเดโมสลับ persona สมมติได้ การใช้งานจริงต้องมี reverse proxy ที่ยืนยันตัวตนและแทนที่ `X-User-Id` จากผู้เรียกก่อนส่งถึงแอป มิฉะนั้นผู้เรียก API สามารถอ้างเป็น persona อื่นได้

โปรไฟล์ที่กฎอ่านจริงมีสามช่องคือ `staff_type`, `department`, `grants_this_year` ตัวเชื่อมของจริงต้องคืนสามช่องนี้ให้ครบ

## หน้าตรวจข้อมูลสำหรับเจ้าหน้าที่

เปิดที่ `/admin` ใส่โทเคนจาก `RISE_ADMIN_TOKEN` กับชื่อผู้ตรวจ หน้านี้มีทั้งรายการข้อมูลเดิมที่รออนุมัติและพื้นที่กักกันเอกสารใหม่

รายการแรกคือข้อความ OCR และข้อความพิมพ์มือจากเอกสารสแกนที่ยังไม่มีใครตรวจ ชิ้นข้อความพวกนี้จะไม่ถูกค้นเจอจนกว่าจะกดอนุมัติ
รายการที่สองคือตัวเลขที่ยังไม่ได้เทียบกับต้นฉบับ แต่ละแถวบอกว่าอ้างอิงเอกสารไหน ข้อไหน หน้าไหน
เจ้าหน้าที่เปิดเอกสารตามนั้น ถ้าตัวเลขตรงก็กดยืนยัน ถ้าไม่ตรงให้แก้ตัวเลขในช่องก่อนแล้วค่อยกด
หน้าเดียวกันมีปุ่ม **เปิด PDF ต้นฉบับ** ทั้งสองรายการ และกางดูข้อความ OCR กับข้อความพิมพ์มือแยกตามหน้าได้
ช่อง **ตรวจ PDF ใหม่ก่อนนำเข้าระบบ** รับไฟล์ที่เลือกจากเครื่องของผู้ดูแลเพื่อแสดงผลอ่านเบื้องต้นเท่านั้น ไม่เขียนลง `data/` หรือโฟลเดอร์เอกสารต้นฉบับ
ช่อง **นำเข้า PDF เป็นฉบับร่าง** ใช้ไฟล์เดียวกัน แต่บันทึกไว้ในพื้นที่กักกันและสร้างชิ้นข้อความให้เปิด PDF เทียบ แก้ข้อความ และแก้ประเภทส่วนได้เมื่ออ่านครบทุกหน้า หากสถานะยัง `needs_ocr` หรือ `failed` ข้อความที่มีอยู่เป็นแบบอ่านอย่างเดียวจนกว่าการลองใหม่สำเร็จ การบันทึกการแก้ไขต้องมีชื่อผู้ตรวจ แต่ยังคงเป็นฉบับร่างและไม่อนุมัติ เมื่อผู้ตรวจเทียบกับต้นฉบับครบทุกหน้า จึงกดเผยแพร่ข้อความได้
การเปิด PDF ต้องใช้โทเคนผู้ดูแล และรับได้เฉพาะชื่อประกาศที่ระบบรู้จักเท่านั้น
ค่าปริยายของโฟลเดอร์ PDF คือ `../../RISE/resource/Docs/Seminar_resource/Funds_resource` เมื่อเทียบจากโฟลเดอร์ `rise-demo`
ถ้าย้ายไฟล์ไปที่อื่น ให้ตั้ง `RISE_SOURCE_DIR` เป็นพาธเต็มใน `.env` ก่อนเปิดเซิร์ฟเวอร์
การเปิดดูไฟล์ไม่เปลี่ยน `draft` หรือ `verified` ต้องให้คนเทียบต้นฉบับครบแล้วกดอนุมัติเอง
การอนุมัติต้องระบุชื่อผู้ตรวจและจำนวนเงินเป็นเลขจำนวนเต็มที่ไม่ติดลบ ระบบไม่รับการยืนยันตัวเลขโดยเว้นช่องจำนวนเงินว่าง

ระบบบันทึกชื่อผู้ตรวจและเวลาไว้ในไฟล์ข้อมูล และสำรองไฟล์เดิมเป็น `.bak` ทุกครั้งที่เขียน
หลังอนุมัติเอกสารใหม่ ข้อความค้นผ่านคำสำคัญและลำดับชั้นได้ในโปรเซสปัจจุบันทันที หากต้องการใช้เวกเตอร์กับข้อความชุดใหม่ให้รัน `python reindex.py` ภายหลัง

ถ้าไม่ได้ตั้ง `RISE_ADMIN_TOKEN` หน้านี้และ API ทั้งหมดของผู้ดูแลจะปิดสนิท ซึ่งเป็นค่าเริ่มต้น

ตัวตนผู้ถามมาจาก header `X-User-Id` ซึ่ง reverse proxy เป็นคนใส่หลังตรวจ session แล้ว
โทเคนผู้ดูแลส่งมาทาง header `X-Admin-Token`
คำขอที่ผิดเงื่อนไขจะได้ 400 ส่วนคำขอที่ถี่เกินจะได้ 429 พร้อมบอกว่าต้องรออีกกี่วินาที
หน้า `/admin`, API ผู้ดูแล และ `/v1/recent` ส่ง `Cache-Control: no-store, private` เพื่อกัน cache ที่แชร์กันเก็บข้อมูลอ่อนไหว
`/v1/recent` จำกัดจำนวนแถวตาม `RISE_AUDIT_MAX_TAIL` อ่านเฉพาะท้ายไฟล์ตาม `RISE_AUDIT_TAIL_READ_BYTES` และข้ามบรรทัด JSONL ที่เสียหรือเขียนค้าง แทนที่จะทำให้หน้าผู้ดูแลล่ม ไฟล์จะหมุนตาม `RISE_AUDIT_MAX_BYTES` และจำนวนสำเนา `RISE_AUDIT_BACKUPS` เพื่อไม่ให้พื้นที่กับหน่วยความจำโตไม่จำกัด

`logs/queries.jsonl` เก็บคำถาม slots คำตอบ อ้างอิง และเวลาที่ใช้ แต่ไม่เก็บตัวโปรไฟล์ เก็บแค่ id ที่ชี้ไปหาโปรไฟล์
เพราะประวัติการรับทุนและประเภทบุคลากรเป็นข้อมูลส่วนบุคคลตาม PDPA และมีอยู่ในระบบต้นทางอยู่แล้ว

## สิ่งที่ยังต้องทำก่อนเปิดใช้จริง

1. **ตรวจตัวเลขที่ OCR อ่านมา** เปิด PDF ต้นฉบับเทียบทีละแถวใน `/admin` ก่อนกดยืนยัน (`verify_report.py` เป็นเพียงตัวช่วย) ตราบที่ยังไม่ยืนยัน ระบบจะไม่ตอบวงเงินจากแถวนั้น
2. **ย้ายขึ้น PostgreSQL** ตอนนี้อ่าน JSON เข้าหน่วยความจำ ของจริงคือตาราง chunks ที่มีคอลัมน์ pgvector ตาราง facts rules users profiles โครงตารางล้อกับไฟล์ JSON ได้เลย
3. **ต่อฐานข้อมูลบุคลากร** แก้ `identity.lookup` ที่เดียว แล้วให้ reverse proxy ใส่ `X-User-Id`
4. **ตัดคำไทยให้ดีขึ้น** `app/modules/retrieval/tokenizer.py` ใช้พจนานุกรมโดเมนบวก trigram ของจริงควรใช้ `pip install pythainlp` แล้วเปลี่ยนไปใช้ `word_tokenize`
5. **ย้ายงาน ingest ไปคิวสำหรับหลายโปรเซส** เดโมมีคิว FIFO หนึ่ง worker ต่อโปรเซส เก็บสถานะลงไฟล์ หยิบงานที่ค้างต่อเมื่อเปิดเซิร์ฟเวอร์ และมีปุ่ม retry แล้ว แต่ worker กับ lock ยังอยู่ในโปรเซสเดียว ของจริงควรใช้ durable worker queue, locking ข้ามโปรเซส, retry policy และหน้าติดตามงาน
6. **ทำข้อมูลโครงสร้างจาก PDF ใหม่ให้ครบ** ตอนนี้แอดมินเผยแพร่ข้อความที่ตรวจแล้วได้ แต่ตัวเลข `ceiling`/`allocated`, กฎสิทธิ์ และชื่อทุนใหม่ยังไม่ถูกสร้างหรืออนุมัติอัตโนมัติ ต้องมีฟอร์มตรวจแถวข้อมูลและทดสอบคำตอบก่อนเปิดใช้เป็นข้อมูลทุนเต็มรูปแบบ
7. **ย้ายตัวนับ rate limit ออกจากหน่วยความจำ** ถ้าวันหนึ่งรันหลาย worker ตัวนับจะแยกกันคนละอัน ต้องใช้ Redis
8. **ตั้ง HTTPS และ reverse proxy** โหมด LAN มีไว้สาธิตชั่วคราว ระบบจริงต้องมี proxy ที่ตรวจ session แล้วใส่ `X-User-Id` ให้
9. **PDPA** โปรไฟล์จริงเป็นข้อมูลส่วนบุคคล ต้องมีฐานทางกฎหมายในการใช้ กำหนดอายุการเก็บ log และจำกัดคนที่เข้าถึงได้
